# Setup, configuration and deployment

## Local demo

Use Node.js 24. Run from the repository root:

```sh
npx pnpm@10.28.2 install --frozen-lockfile
npx pnpm@10.28.2 demo:setup
npx pnpm@10.28.2 dev
```

Visit `http://localhost:3000/bn-BD`. The English version is `/en-BD`. The demo password is generated in `.env`; select an identity in the sign-in form. No demo credentials are hard-coded. Optional providers are disabled. Local demo storage is suitable for a trusted local demonstration only.

## Environment inventory

All secrets belong in a deployment secret store. No `NEXT_PUBLIC_` service secret is used. Restart/rebuild when changing build-time policy settings.

| Variables | Meaning / requirement |
|---|---|
| `NODE_ENV`, `APP_URL` | Development/production and canonical HTTPS origin |
| `DEMO_MODE` | Explicitly enables synthetic identity login; must be `false` for real public service |
| `DATA_BACKEND`, `DATA_DIR` | `demo` or `postgres`; local private path, resolved relative to workspace root |
| `DATABASE_URL` | Runtime PostgreSQL URL; use a dedicated login granted `denguespot_runtime` |
| `DIRECT_DATABASE_URL` | Migration owner URL; never give schema owner credentials to the running web service |
| `TEST_DATABASE_URL` | Dedicated synthetic test database; real integration tests skip without it |
| `DATABASE_HOST`, `DATABASE_USER`, `DATABASE_PASSWORD`, `DATABASE_NAME` | Alternative AWS URL construction, only when `DATABASE_URL` is absent |
| `DATABASE_SSL`, `DATABASE_CA_FILE` | Production `true`; optional trusted CA PEM file. Certificate verification is never disabled |
| `POSTGRES_PASSWORD` | Local Compose database only; generated by demo setup |
| `SUPABASE_URL`, `SUPABASE_ANON_KEY` | Verified Auth adapter; required for real sign-in |
| `SUPABASE_SERVICE_ROLE_KEY` | Server-only Supabase private storage adapter credential |
| `STORAGE_BACKEND` | `local` only in demo; `supabase` or `s3` for production |
| `STORAGE_BUCKET_ORIGINAL`, `STORAGE_BUCKET_REDACTED` | Private Supabase buckets, default `originals` and `derivatives` |
| `AWS_REGION`, `S3_BUCKET`, `S3_KMS_KEY_ID` | S3 evidence adapter; prefer IAM task credentials, never browser access keys |
| `PUBLIC_LOCATION_GRID_METERS` | Default 150; validated range in service. Do not reduce without a privacy review |
| `DUPLICATE_RADIUS_METERS`, `DUPLICATE_WINDOW_DAYS` | Defaults 75 m / 7 days |
| `QR_SIGNING_SECRET`, `TRACKING_TOKEN_PEPPER`, `AUDIT_HASH_SECRET`, `SESSION_SECRET` | Independent random secrets, at least 32 characters; local setup uses 32 random bytes encoded as hex |
| `WEBHOOK_SIGNING_SECRET` | Future signed callback boundary; separate random secret |
| `DEMO_LOGIN_PASSWORD` | Random demo-only password; no effect when demo mode is disabled |
| `AI_TRIAGE_ENABLED`, `OPENAI_API_KEY`, `OPENAI_MODEL` | Disabled by default; optional reviewed-image advisory adapter. Model must support configured structured image input |
| `OCR_ENABLED`, `GOOGLE_CLOUD_PROJECT`, `GOOGLE_APPLICATION_CREDENTIALS` | Optional adapter integration inputs; Google adapters currently accept an injected OAuth token callback |
| `SPEECH_ENABLED` | Optional Bangla speech adapter; not wired into the citizen UI |
| `SMS_ENABLED`, `SMS_PROVIDER`, `SSL_WIRELESS_API_KEY`, `SSL_WIRELESS_SENDER_ID` | Reserved live-provider configuration. Flags alone do not implement contract transport, OTP UI or callbacks |
| `MAP_TILE_URL`, `MAP_ATTRIBUTION` | Raster XYZ provider URL/attribution. Default OpenStreetMap standard raster for modest demo use; custom hosts also need CSP allowlisting in Next config |
| `GEOCODING_PROVIDER` | `manual` is implemented; no address is sent to a geocoder by default |
| `PRIVACY_CONTACT` | Visible privacy contact; configure a staffed address/process before launch |
| `SENTRY_DSN` | Reserved configuration; no Sentry SDK integration is claimed |

Do not reuse the demo secrets in production. Rotation of the tracking pepper invalidates existing anonymous credentials; versioned key rotation and account recovery need a migration plan. Audit-key rotation likewise needs versioned verification. Rotate provider credentials independently.

Default tiles follow the [OSM tile policy](https://operations.osmfoundation.org/policies/tiles/): visible attribution, normal browser caching and an origin-only cross-origin referrer; no offline tile download or prefetch. Configure an approved hosted/self-hosted tile provider for production volume and availability. Automated E2E uses an intentionally unavailable local tile URL to exercise the fallback without requesting community tile servers. Open the demo through the configured `APP_URL` (default `http://localhost:3000`); a different origin can be rejected by the write-origin check.

## PostgreSQL/PostGIS and migrations

Supported baseline: PostgreSQL 17 with PostGIS 3.5+. The local verification used PostgreSQL 17.11/PostGIS 3.6.2. Start a dedicated database with Docker, Supabase or an approved managed service. Set the owner migration URL and runtime URL privately, then:

```sh
npx pnpm@10.28.2 db:migrate
npx pnpm@10.28.2 db:seed
```

Set `DATA_BACKEND=postgres` for seed/runtime. Seed is **synthetic staging/demo data only**. It preserves a nonempty dataset. The two ordered migrations are tracked in `schema_migrations`, each applied in a transaction:

1. `001_core.sql`: application tables, separate exact/public spatial storage, GiST indexes, public view, RLS/revocations, immutable event/audit triggers.
2. `002_runtime_permissions.sql`: non-login trusted-server permission group, explicit RLS policies and narrowly scoped grants. Runtime cannot update identities or rewrite audit/event records. It has no schema/role administration rights.

Provision a login using your database's secret workflow, grant `denguespot_runtime` to it, and use that login in the runtime secret. Never grant this group to Supabase `anon` or `authenticated`. Supabase clients cannot directly query the application tables; all access passes through the BFF. Keep the migration owner URL out of runtime web/worker secrets. In managed environments where role creation requires an administrator, have that administrator apply migration 002; do not silently weaken permissions.

Production has no auto-seed. Load verified authority polygons in `jurisdictions.boundary` (MultiPolygon/EPSG:4326), matching metadata in `data`, profiles linked to verified Auth IDs, and `organization_memberships`. The demo writer creates bounding boxes; an official boundary import/admin UI is not supplied. Confirm that every pilot service area has an accountable organization and staffing arrangement before accepting real reports.

## Docker local stack

Requires Docker Desktop with Linux containers or Docker Engine/Compose on Linux. `.env` must contain a strong `POSTGRES_PASSWORD`.

```sh
docker compose up -d postgres
docker compose build web worker
docker compose run --rm worker pnpm db:migrate
docker compose run --rm worker pnpm db:seed
docker compose up -d web worker
docker compose ps
```

Compose is an explicitly labeled demo: PostGIS, web and worker use synthetic identities and private local media volume; ports bind to loopback. Docker image targets run as non-root. The web image uses Next standalone output. The worker image also carries migration/seed tooling for local orchestration; a minimized production worker image is a follow-up hardening item. No Docker daemon was available during this build, so these commands and image builds remain unverified locally; CI includes both image builds.

## Deploy a demo to Vercel + Supabase

Requires your own Vercel account/project and Supabase project with PostGIS, database access and **private** evidence buckets. Public deployment creates cloud resources and may incur charges; no cloud project or URL was created by this work.

1. In Vercel, set project Root Directory to `apps/web`, framework Next.js, install command `cd ../.. && pnpm install --frozen-lockfile`, build command `pnpm build`, Node.js 24. Allow access to files outside the root directory for the workspace packages.
2. Configure encrypted environment variables: `DEMO_MODE=true`, `DATA_BACKEND=postgres`, TLS-verified database URL, Supabase URL/anon/service credentials, `STORAGE_BACKEND=supabase`, bucket names, `APP_URL`, independent signing secrets and a random `DEMO_LOGIN_PASSWORD`. Keep all optional provider flags false. Use a demo-only database and synthetic data; do not accept real personal reports in this environment.
3. Locally set the demo database owner URL, migrate, then seed it. Use your private `.env` or shell environment; never paste credentials into source or command-history URLs.
4. Link and deploy from the repository root:

```sh
npx pnpm@10.28.2 dlx vercel link
npx pnpm@10.28.2 dlx vercel pull --yes --environment=preview
npx pnpm@10.28.2 dlx vercel build
npx pnpm@10.28.2 dlx vercel deploy --prebuilt
```

5. Configure the resulting canonical origin/alias in `APP_URL`, redeploy as needed, and verify `/api/v1/health`, `/api/v1/ready`, both locale funnels and private-access denials.

Vercel's serverless request-size limit can be lower than this app's 8 MB image policy; use small demo photos (under 4 MB) and verify your plan's limit. Production needs a direct signed-upload workflow or a runtime with sufficient bounded request capacity before claiming full 8 MB support. A persistent worker and scheduled retention run elsewhere (for example ECS/container service); a Vercel web deployment does not start the infinite worker loop. No hosted demo was deployed because cloud credentials were unavailable.

## Controlled production delivery

Use separate staging/production databases, private buckets, secrets and Auth projects. `.github/workflows/ci.yml` runs checks, real PostGIS tests, browser tests and Docker builds. `security.yml` audits dependencies and runs static/secret checks. `staging.yml` provides a manually triggered Vercel preview. `production.yml` checks an approved staging health URL before deployment; GitHub environment reviewers, allowed branches and required CI status must be configured in the repository. These workflow files are templates and were not executed on GitHub.

Populate `VERCEL_TOKEN`, `VERCEL_ORG_ID`, `VERCEL_PROJECT_ID` in the appropriate GitHub environments. Production runtime must set `DEMO_MODE=false`, use dedicated runtime DB permissions, private storage and provisioned identities. Staff require verified Supabase `aal2`; the scaffold enforces this but does not supply enrollment/challenge/recovery screens. Complete and test your identity flow before launch. Disable optional processors unless consent, contracts and transfer review are approved.

After staging validation and all release gates in `IMPLEMENTATION_STATUS.md`:

```sh
npx pnpm@10.28.2 dlx vercel pull --yes --environment=production
npx pnpm@10.28.2 dlx vercel build --prod
npx pnpm@10.28.2 dlx vercel deploy --prebuilt --prod
```

Run migrations in a controlled runner with owner credentials, with a verified backup first. Use forward-compatible additive changes so the previous application can run during rollback. Never run destructive schema changes from a web startup hook.

## AWS reference

See `infra/terraform/README.md` and environment examples. Modules cover VPC, private encrypted RDS, private KMS-encrypted S3, ECS web/worker, HTTPS ALB, WAF and logs. They require AWS credentials, ACM/DNS, ECR image digests, an application secret, approved region, remote state and controlled migration networking. The reference still wires a managed DB-owner secret until replaced with a provisioned runtime login: that is an explicit release blocker.

```sh
terraform -chdir=infra/terraform init
terraform -chdir=infra/terraform fmt -check -recursive
terraform -chdir=infra/terraform validate
terraform -chdir=infra/terraform plan -var-file=environments/staging/terraform.tfvars
terraform -chdir=infra/terraform apply -var-file=environments/staging/terraform.tfvars
```

Copy the example to a local `terraform.tfvars`, replace placeholders and review the plan/costs before applying. Validation passed locally; no authenticated plan or apply was run. Schedule retention, configure alert destinations and verify backup restoration. See `RUNBOOK.md` for operation and rollback.
